## (2) iPhoneへの無料プッシュ通知

### Web Push（iOS）の条件
- WebKit公式: 「A web app that has been added to the Home Screen can request permission to receive push notifications.」許可要求は「in response to direct user interaction」（購読ボタンのタップ）のとき。iOS/iPadOS 16.4以降。標準のPush API・Notifications API・Service Workerで動く。サーバー側は `*.push.apple.com` を許可する必要があり、Apple Developer Program加入は不要。https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/
- VAPID鍵: WebKitの記事には記載なし（確認できず）。一般にはWeb Push送信側がVAPID鍵ペアを持つ。公開鍵を購読時に渡し、秘密鍵は送信側だけが保管する（これは一般知識で、今回の公式ページでは未確認）。
- ホーム画面追加済みのPWAでないと購読できない。Safariのタブ上では不可。

### 送信元の候補
| 方式 | 無料枠（公式） | 購読情報の保管 | 利用者の新規アカウント |
|---|---|---|---|
| A. GitHub Actions（既存の収集ワークフローから送る） | 公開リポジトリは無料（既に利用中） | リポジトリの**Secrets**（公開されない）。アプリが表示した購読JSONを、利用者がGitHubのWeb画面で貼る | 不要（既存のGitHubのみ） |
| B. | C. ntfy.sh | 登録・無料で使える（FAQ「without signup and free of charge」）。日次の上限数値は記載なし | なし（トピック名のみ） | 不要（iOSはntfyアプリのインストールが必要） |

### ntfy.shの評価
- トピック名がパスワード代わり: FAQ「the topic name is your password」。ACLなしでは、トピック名を知る人は誰でも送受信できる。長いランダム名にすれば実用上は強いが、漏れたら終わり。
- プライバシー: 「ログにはトピック名とIPアドレスが含まれる」（用途は障害調査とレート制限）。メッセージ内容は既定でログに残さない。iOSはFCM経由（APNs）で配信と明記。メッセージ保持は既定12時間。https://docs.ntfy.sh/privacy/ https://docs.ntfy.sh/faq/
- 注意: FAQはiOSアプリを「very bare bones and quite frankly a little buggy」と記述。IPが「pretty quickly」BANされうる。
- 公開リポジトリのActionsから送る場合、トピック名はSecretsに置く必要がある。通知本文に載せる情報が第三者に見えうる点にも注意。
- 評価: 手軽だが、iOSアプリが別途必要で信頼性に不安。第2候補。

## 推奨: 方式A（GitHub Actions＋Web Push、購読情報はGitHub Secrets）

理由: 新しいアカウントが不要、課金リスクなし（公開リポジトリのActions無料、既に運用中）、購読情報は公開されない。Cloudflareは便利だが追加アカウントが必要で、まず不要。

### できること／できないこと
- できる: 収集ワークフローが新しい重要IR（監視銘柄の業績修正・決算発表日など）を見つけたとき、iPhoneに通知。
- できない／弱い: ①定時実行は遅れる（実測で約37分遅れ）ため、「発表の何分前」のような秒単位の通知は不可。②**個人のメモ・再確認日はブラウザ内にしかなく、Actionsは知らない**ので、再確認日の通知は従来どおり .ics（iPhone標準カレンダーのアラーム）を使う。再確認日をSecretsに入れる手もあるが運用が重い。③購読が失効（iOSで通知拒否・アプリ削除・長期未使用）すると送信は失敗する。

### 次の実装作業（開発側）
1. アプリに「通知を有効にする」ボタン、Service Worker（push／notificationclick）、購読JSONの表示とコピー画面を追加。購読JSONは画面表示のみで、サーバーに自動送信しない。
2. VAPID鍵ペア生成の手順（利用者のPCでPythonスクリプトを実行。秘密鍵は画面に出さずファイルにも残さないよう注意）。
3. collectワークフローに送信ステップを追加（Pythonの標準的なWeb Pushライブラリ、例 pywebpush。今回の調査では未確認なので導入前に最新版・ライセンスを確認）。送るのは「新規の重要イベントのタイトルと短い要約」のみ。1実行あたりの送信数に上限を設け、失敗（404/410）は購読失効として記録のみ。
4. Secrets未設定ならスキップする（エラーにしない）。ログに購読情報・秘密鍵を出さない。
5. 「通知は実機未確認」の表示を、実機確認が済むまで残す。

### 利用者の操作
1. iPhone（iOS 16.4以上）でSafariからアプリを開き、共有メニュー→「ホーム画面に追加」。
2. ホーム画面のアイコンから起動し、「通知を有効にする」をタップして許可。
3. 画面に出た購読JSONをコピー（iPhoneからPCへ送る手段は自分宛メッセージ等）。
4. GitHubのリポジトリ設定→Secretsに、購読JSONとVAPID秘密鍵を貼り付け（GitHubへのログインは利用者本人）。
5. 通知が実際に届くか確認。

### 実機でしか確認できない点
- ホーム画面追加後の許可ダイアログ、通知の表示、タップでアプリが開くか。
- アプリを閉じた状態・ロック画面での到達、集中モード時の挙動。
- 購読の失効タイミング（iOSは長期間使わないと失効しうる：確認できず）。
